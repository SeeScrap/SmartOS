# SmartOS

*[English version](README.md) — ฉบับเต็มพร้อมบันทึกการวัดทุก stage อยู่ที่นั่น*

ระบบปฏิบัติการที่เขียนขึ้นเองสำหรับ ESP32-S3 สร้างจากชั้นเคอร์เนลขึ้นมา
มันไม่ได้วางทับบน FreeRTOS — **มันเป็นเจ้าของคอร์หนึ่งคอร์**

---

## ติดตั้ง

คำสั่งเดียวจบตั้งแต่ clone มาใหม่ ต้องมี [PlatformIO](https://platformio.org/)
และเสียบบอร์ดที่ช่อง **USB ของชิปเอง** (ช่องที่เขียนว่า USB ไม่ใช่ UART)

```
git clone https://github.com/SeeScrap/SmartOS
cd SmartOS
pio run -t upload -t monitor
```

PlatformIO จะดึง ESP-IDF มาให้เอง และดึง component ของคนอื่นเพียงตัวเดียวที่
โปรเจกต์นี้ใช้ — littlefs — ตามเวอร์ชันที่ตรึงไว้ใน `dependencies.lock` ซึ่งเป็น
เวอร์ชันเดียวกับที่ทุกตัวเลขในเอกสารนี้ถูกวัด บิลด์ครั้งแรกราวห้านาที หลังจากนั้น
ไม่กี่วินาที (วัดจริงบนเครื่องสะอาด: **3 นาที 41 วินาที**)

**สองเรื่องที่ถ้าไม่มีใครบอกจะเสียเวลาไปครึ่งวัน:**

* **ห้ามมีช่องว่างในพาธของโปรเจกต์** ระบบบิลด์ของ ESP-IDF ปฏิเสธตรงๆ
* **บน Windows ให้บิลด์จากบรรทัดคำสั่งด้วย `PLATFORMIO_BUILD_DIR=.pio/cli`**
  เพราะส่วนขยาย VS Code จะบิลด์ลง `.pio/build` เองทุกครั้งที่ `platformio.ini`
  เปลี่ยน และการที่ตัวบิลด์สองตัวใช้โฟลเดอร์เดียวกันคือที่มาของอาการ
  "บิลด์พังแบบไม่มีเหตุผล" ทุกครั้งในโปรเจกต์นี้

## เปิดเครื่องแล้วเจออะไร

หน้าบูตที่มีตัวหมุน แล้วเข้า **Home** — หน้า launcher บนภาพพื้นหลัง พร้อมแอปที่
มากับระบบ: ตัวนับ, กล่องเด้ง, สโคป ADC, งู, แอปจดบันทึกที่มีแป้นพิมพ์บนจอ,
หน้าตั้งค่า, ตัวอ่าน log และ task manager ที่มีหน้า performance

![Home](docs/screens/home_wallpaper.png)

ปุ่มหกปุ่มคุมทุกอย่าง: UP/DOWN เลือก, OK เปิด, **กด BACK ค้าง** ปิดแอป,
**DOWN+BACK** ย่อแอปโดยให้มันทำงานต่อ ปุ่มบนบอร์ดนี้ยังไม่ได้ต่อสาย
ระหว่างที่ยังไม่ได้บัดกรี สั่งผ่านสายแทนได้:

```
s3> key down down ok      ส่งเหตุการณ์ชุดเดียวกับที่ปุ่มจริงส่ง
s3> ps                    งานของเคอร์เนล แล้วต่อด้วยแอป พร้อม CPU
s3> free                  RAM ภายใน, PSRAM, พูลของเคอร์เนล
s3> screenshot            บันทึกหน้าจอเป็น PNG ผ่าน tools/screenshot.py
s3> help                  ที่เหลือ
```

บอร์ดพิมพ์ผลตรวจตัวเองทุกครั้งที่บูต `-t monitor` จึงควรอ่าน — **75 รายการใน
บิลด์ปกติ** และ 159 รายการเมื่อใส่ `-D SMARTOS_TEST_APPS` หรือสั่ง
`python tools/boot_check.py` ให้รีเซ็ตบอร์ด นับให้ และเทียบ**รายชื่อเคส**กับ
เส้นฐานที่คอมมิตไว้ เพื่อให้รู้ตัวเมื่อมีเทสหยุดทำงานไปเงียบๆ ไม่ใช่แค่ตอนมันไม่ผ่าน

## เขียนแอปแล้วติดตั้ง โดยไม่ต้องแฟลชใหม่

นี่คือส่วนที่ทำให้มันเป็นระบบปฏิบัติการ ไม่ใช่แค่โปรแกรม แอปคือ**ไฟล์** ส่งเข้า
บอร์ดผ่านสาย USB เส้นเดิม โผล่ใน Home ข้างแอปที่มากับระบบ และอยู่รอดการถอดไฟ
**เฟิร์มแวร์ไม่ถูกบิลด์ใหม่และไม่ถูกแตะ** — ตรวจด้วย `esptool verify_flash`
ซึ่งตอบว่า "verify OK (digest matched)" หลังทำทั้งหมดแล้ว

```
app tally {
    order 100
    var count

    on draw {
        if (full) { text(8, 6, "Tally", 0x56BF, 2) }
        text_bg(8, 50, fmt("pressed %d times", count), 0xFFFF, 0, 1)
    }

    on event {
        if (ev_type == 0 && ev_a == 1) { count = count + 1  invalidate() }
    }
}
```

```
python tools/sappc.py examples/apps/tally.sap tally.app    # 246 ไบต์
python tools/install_app.py tally.app
  tally installed; it is in Home now
```

`tools/install_app.py` ทำ `--list` กับ `--remove` ได้ด้วย ส่วนภาษา เครื่องที่มันรัน
และเหตุผลที่**ไม่ใช่โค้ดเนทีฟ** อยู่ใน [ฉบับอังกฤษ หัวข้อ Stage 7](README.md#stage-7---apps-the-user-installs)
พูดสั้นๆ คือชิปนี้ต้องปิดการป้องกันหน่วยความจำทั้งระบบอย่างถาวรถึงจะรันโค้ดที่
โหลดมาได้ จึงเลือกให้แอปถูก**ตีความ**แทน — แล้วกลับกลายเป็นว่าปลอดภัยกว่าแอป
ที่คอมไพล์เข้าไปในเฟิร์มแวร์เสียอีก

## เขียนโปรแกรมบนเคอร์เนลล้วน

ไม่มีหน้าจอ ไม่มีแอป ไม่มีระบบไฟล์ — มีแค่เคอร์เนล แบบเดียวกับที่ใช้ RTOS

```c
#include "smartos.h"            // พื้นผิวทั้งหมดอยู่ในไฟล์นี้ไฟล์เดียว

static k_mutex_t lock;

static void worker(void *arg) {
    for (int i = 0; i < 1000; ++i) {
        k_mutex_lock(&lock);
        counter++;
        k_mutex_unlock(&lock);
    }
    k_exit();
}
```

[examples/kernel_blink/](examples/kernel_blink/) เป็นโปรเจกต์ PlatformIO แยก
ต่างหาก บิลด์กับ component ของเคอร์เนลและของ ESP-IDF อีกสามตัว **ไม่มีส่วนใด
ของระบบปฏิบัติการอยู่ในนั้นเลย** การที่มันลิงก์ติดและรันได้คือเหตุผลที่ชั้นต่างๆ
ถูกจัดแบบนี้ — แฟลช 175 KB แรม 17 KB และไฟกะพริบจริง

```
cd examples/kernel_blink
pio run -t upload
```

## โครงสร้าง

เคอร์เนลตัวนี้ไม่ได้วางทับบน FreeRTOS แต่**เป็นเจ้าของ core 1 ทั้งคอร์** — ESP-IDF
ถูกตั้งค่าเป็น unicore ทำให้ FreeRTOS ไม่เคยสตาร์ตคอร์ที่สอง เคอร์เนลจึงเข้าไปยึด
พร้อมตารางเวกเตอร์ของตัวเอง ตัวจับเวลาของตัวเอง ตัวจัดคิวของตัวเอง และตัวจัดการ
หน่วยความจำของตัวเอง ส่วน core 0 อยู่ต่อเพื่อดูแล USB แฟลช และ PSRAM
และรับงานที่ส่งข้ามมาทาง mailbox

```
 CORE 0                          CORE 1
 IDF + FreeRTOS                  SmartOS
  - คอนโซล USB                    - ตารางเวกเตอร์   (kvectors.S)
  - แฟลช / PSRAM                  - tick CCOMPARE0  (ktime.cpp)
  - คนงานฝั่ง mailbox              - ตัวจัดคิว        (ksched.cpp)
                                  - การสลับงาน      (kswitch.S)
                                  - ตัวจัดการหน่วยความจำ (kheap.cpp)
        ^                                |
        +------- ช่องงานของ kmbox --------+
```

> **ข้อแก้ไข** บันทึกรายสเตจในฉบับภาษาอังกฤษเขียนเลขไว้สูงกว่านี้ (51 และ 134
> ต่อมา 51 และ 135) เพราะนับทุกบรรทัดใน log ที่ลงท้ายด้วย `OK` ซึ่งมีสามบรรทัด
> ที่ไม่ใช่เทส ได้แก่ log ของ ESP-IDF เอง กับ task สาธิต `[consumer]` และ
> `[mbox]` ที่รายงานผลของตัวเอง ไม่มีอะไรถดถอย — เลขผิด ไม่ใช่เฟิร์มแวร์ผิด
> เลขจริงตอนนั้นคือ 48 กับ 132 และที่เป็น 75 กับ 159 ตอนนี้เพราะชุดทดสอบของ
> stage 7 สองชุด (เครื่องบายท์โค้ดกับตัวโหลด) เคยรันเฉพาะเมื่อใส่แฟล็ก
> ตั้งแต่ S7h มันรันทุกครั้งที่บูตเหมือนชุดอื่น

สร้างเพื่อบอร์ดตัวเดียว แต่เขียนให้เอาไปทำต่อได้:
[CONTRIBUTING.th.md](CONTRIBUTING.th.md) บอกวิธี build กฎที่ต้องระวังบน core 1
และวิธีเพิ่มแอปหรือการทดสอบ — [สัญญาอนุญาต MIT](LICENSE)

## ฮาร์ดแวร์

| ส่วน | รายละเอียด |
|---|---|
| ชิป | ESP32-S3-DevKitC-1 **N16R8** — แฟลช QIO 16 MB, PSRAM octal 8 MB |
| จอ | **SPI TFT 2.4" 240x320 ชิป ST7789V** — ใช้แนวนอน 320x240 |
| ทัช | XPT2046 บนบัส SPI เดียวกัน (ยังไม่ได้ใช้) |
| ข้อสังเกต | ขา SDO ของโมดูลไม่ได้ต่อถึงชิปควบคุม จึงอ่านรุ่นจอไม่ได้ ต้องระบุด้วย `-D LCD_FORCE_CTRL` |
| ปุ่ม | 6 ปุ่มลง GND อ่านด้วย pull-up ภายใน |

การต่อสายอยู่ใน [src/board/pins.h](src/board/devkitc_n16r8.h) **ห้ามใช้ GPIO 26-37**
บนโมดูลนี้ — เป็นขาของแฟลชและ PSRAM แบบ octal

**ปุ่มใช้สายสองเส้นต่อปุ่ม**: ขาหนึ่งไป GPIO อีกขาไป GND เท่านั้น ไม่ต้องใช้ตัวต้านทาน
UP 4, DOWN 5, LEFT 6, RIGHT 7, OK 15, BACK 16 — ถ้าเป็นปุ่ม tactile 4 ขาให้ใช้
ขาทแยงมุม และถ้ายังไม่ได้ต่อปุ่ม ก็ใช้ `key up` / `hold back` ในเชลล์แทนได้

## เขียนโค้ดบน SmartOS

เป็นงานคนละแบบสามงาน และระบบแยกความต่างนี้ให้เห็นชัด มีตัวอย่างที่ทำงานได้จริง
ของทั้งสามแบบอยู่ใน **[examples/](examples/)**

| | โปรแกรมบนเคอร์เนล | แอปในเฟิร์มแวร์ | แอปที่ผู้ใช้ติดตั้งเอง |
|---|---|---|---|
| คืออะไร | โปรเจกต์ของตัวเอง ชี้มาที่ `components/smartos` | ไฟล์เดียววางใน `src/apps/` | ไฟล์ที่ส่งผ่านสาย USB |
| เขียนด้วย | C++ ใช้ `smartos.h` | C++ ใช้ `smartos_app.h` | ภาษาเล็กๆ คอมไพล์ด้วย `tools/sappc.py` |
| ได้อะไร | งาน ล็อก คิว นาฬิกา heap `klog` | ทั้งหมดนั้น บวกหน้าจอ เหตุการณ์ ไฟล์ ค่าที่จำไว้ บันทึก ชุดควบคุม ปุ่ม | system call ที่มีหมายเลข 19 ตัว |
| ใครเริ่ม | `app_main` ของตัวเอง | ผู้ใช้ จากหน้า Home | ผู้ใช้ จากหน้า Home |
| ต้องบิลด์ OS ใหม่ | ไม่ | **ใช่** | **ไม่** |
| ถ้ามันพัง | ทั้งบอร์ด | ทั้งบอร์ด | ตัวมันเองเท่านั้น |
| ถ้ามันวนไม่รู้จบ | watchdog | ถูกฆ่าใน 2 วินาที | ถูกหยุดที่คำสั่งที่ 20,000 |
| ตัวอย่าง | [examples/kernel_blink/](examples/kernel_blink/) — แฟลช 175 KB แรม 17 KB | [src/apps/app_hello.cpp](src/apps/app_hello.cpp) — คัดลอกไป | [examples/apps/tally.sap](examples/apps/tally.sap) — 246 ไบต์ |

`examples/kernel_blink` เป็นโปรเจกต์ PlatformIO แยกต่างหาก บิลด์กับ component
ของเคอร์เนลและ component ของ ESP-IDF อีกสามตัว **ไม่มีส่วนใดของระบบปฏิบัติการ
อยู่ในนั้นเลย** การที่มันลิงก์ติดและรันได้คือเหตุผลที่ชั้นต่างๆ ถูกจัดแบบนี้

คอลัมน์ที่สามคือ stage 7 และเป็นอันที่เปลี่ยนว่าบอร์ดนี้คืออะไร —
**ติดตั้งแอปแล้วไม่ต้องแฟลชเฟิร์มแวร์ใหม่** แอปไปอยู่บนพาร์ทิชัน `storage`
ลงทะเบียนตัวเองตอนบูตครั้งถัดไป แล้วโผล่ในหน้า Home ข้างแอปในตัว

มันถูก**ตีความ**ไม่ใช่โค้ดเนทีฟ ซึ่งเป็นการตัดสินใจจากการวัด ไม่ใช่ข้อจำกัดที่
หลบเลี่ยงมา: S7a ถามฮาร์ดแวร์ตรงๆ แล้วได้คำตอบว่าชิปนี้ไม่มี heap ที่รันได้
บัสคำสั่งเข้าไม่ถึง PSRAM เลย และโค้ดที่โหลดมาจะรันได้ก็ต่อเมื่อ**ปิดการป้องกัน
หน่วยความจำของชิปทั้งระบบอย่างถาวร** จึงเลือกไม่ปิด

ผลที่ได้กลับปลอดภัยกว่าของเดิม: เครื่องบายท์โค้ดไม่มีคำสั่งไหนรับที่อยู่เลย
แอปที่ติดตั้งจึงสร้างพอยน์เตอร์ไม่ได้ ทุกทางออกเป็น error ที่ตรวจจับได้
ไม่ใช่ fault และทุกการเรียกกลับถูกตัดที่ 20,000 คำสั่ง รายละเอียดทั้งหมด
(รวมผลวัด 3.4 ล้านคำสั่งต่อวินาที และ `esptool verify_flash` ที่ยืนยันว่า
พาร์ทิชันเฟิร์มแวร์ไม่ถูกแตะเลย) อยู่ใน [README ฉบับภาษาอังกฤษ](README.md#stage-7---apps-the-user-installs)

ค่าตั้งค่าทั้งระบบอยู่ในไฟล์เดียว **[include/smartos_config.h](include/smartos_config.h)**
18 หมวด ทุกค่าห่อ `#ifndef` ให้ override จาก `build_flags` ได้โดยไม่ต้องแก้ไฟล์
และค่าที่มาจากการวัดบนบอร์ดพกคำอธิบายการวัดไปด้วย บอร์ดที่กำลังทำงานจะบอกเองว่า
ถูกสร้างมาด้วยค่าอะไร — สี่บรรทัดแรกถัดจากข้อมูลฮาร์ดแวร์คือค่าที่มันมีจริง

## การพอร์ตไปชิปอื่น

ส่วนที่ต้องเปลี่ยนถูกแยกไว้แล้ว และการแยกถูกบังคับด้วยระบบบิลด์ ไม่ใช่แค่เขียนไว้

| | เก็บอะไร | เปลี่ยนเมื่อ |
|---|---|---|
| `components/smartos/kernel/` | ตัวจัดคิว ล็อก heap นาฬิกา mailbox ตัวรายงานข้อผิดพลาด | ไม่ต้องเปลี่ยน — ไม่มีเฮดเดอร์ของ ESP-IDF หรือของชิปเลย |
| `components/smartos/arch/xtensa/` | ตารางเวกเตอร์ การสลับคอนเท็กซ์ คำสั่งอะตอมมิก การปิดอินเทอร์รัปต์ | ย้ายไปชุดคำสั่งอื่น |
| `components/smartos/port/` | การปลุกคอร์ 1 อินเทอร์รัปต์ข้ามคอร์ คอนโซล การแบ่ง heap | ย้ายไปชิปอื่น |

บรรทัด `REQUIRES` ใน [components/smartos/CMakeLists.txt](components/smartos/CMakeLists.txt)
คือคำประกาศการพึ่งพา และ CMake บังคับมัน: ESP-IDF เจ็ดตัว ทั้งหมดถูกเรียกจาก
`port/` ไฟล์ในเคอร์เนลที่เอื้อมหาตัวอื่นจะทำให้บิลด์หยุดทันที

สิ่งที่การพอร์ตต้องจัดหาคือฟังก์ชันไม่กี่ตัวใน
[components/smartos/port/kport.h](components/smartos/port/kport.h) — การวางโค้ด
ใน RAM คอนโซล การหน่วงระดับไมโครวินาที หมายเลขคอร์ อินเทอร์รัปต์ข้ามคอร์ และการ
แบ่ง heap ครั้งเดียวตอนบูต บวกกับการปลุกคอร์ที่สอง **จงใจทำเป็น inline กับ
สัญลักษณ์ลิงก์ไทม์ ไม่ใช่ตารางฟังก์ชันพอยน์เตอร์** เพราะการสลับคอนเท็กซ์กับ
สปินล็อกวัดกันเป็นจำนวนคำสั่ง ของบนเส้นทางนั้นต้องตัดสินตอนคอมไพล์

## สิ่งที่สร้างขึ้นมา ทีละชั้น

**เคอร์เนล** — ตารางเวกเตอร์และตัวบันทึก fault ของตัวเอง, การสลับงานเขียนด้วย
Xtensa assembly, ตัวจัดคิวแบบ preemptive ที่สลับงานได้จากใน interrupt,
mutex/semaphore/queue, ตัวจัดการหน่วยความจำสองพูล (128 KB ภายใน + 4 MB PSRAM)
พร้อมแนวกันชนใต้ stack ทุกเส้น

**สองคอร์** — เริ่มจาก AMP (คอร์ละระบบ) แล้วขยายเป็น SMP ที่ตัวจัดคิวเดียว
คุมทั้งสองคอร์

**ชั้นบริการ** — event bus, app model (8 ช่อง เปิด/ปิด/บังคับปิด/ย่อ),
ระบบไฟล์ LittleFS ที่ทนไฟดับ, settings, system log ที่หมุนไฟล์เองและจำกัดอัตราเขียน,
เชลล์ผ่าน USB

**กราฟิก** — framebuffer ใน PSRAM, damage tracking (ส่งเฉพาะส่วนที่เปลี่ยน),
หนึ่ง SPI transaction ต่อสี่เหลี่ยม, ฟอนต์ 5x8 — วัดได้ 15.4 มิลลิวินาทีต่อเฟรมเต็มจอ
(ประมาณ 65 เฟรมต่อวินาที, 9.7 MB/s)

**ส่วนผู้ใช้** — หน้า launcher, task manager ที่มีหน้า performance,
ตัวอ่าน log, แป้นพิมพ์บนจอที่ใช้ปุ่ม 6 ปุ่ม, boot screen, ภาพพื้นหลัง

**แอปที่ติดตั้งเองได้** — เครื่องบายท์โค้ด 33 opcode, system call 19 ตัว,
ภาษาและคอมไพเลอร์, ติดตั้ง/ถอนผ่านสาย USB โดยไม่แตะพาร์ทิชัน
เฟิร์มแวร์เลย — ยืนยันด้วย `esptool verify_flash`

**วิทยุ** — 2.4 GHz เท่านั้น (Wi-Fi b/g/n + BLE 5) สแกนคลื่นได้ พร้อมเครื่องมือ
สำรวจบนคอมสำหรับเปรียบเทียบเสาอากาศ

## ถ้าจะเอาคอร์ 0 มาด้วยล่ะ

คำถามที่ตามมาเองคือ SmartOS ยึดทั้งชิปได้ไหม ทั้งสองคอร์ ไม่ต้องแบ่งให้ FreeRTOS
คำตอบมาจากการวัด ไม่ใช่การเดา และไม่ใช่คำตอบที่คำถามคาดไว้

**FreeRTOS ไม่ได้เอาทรัพยากรไปเลย** นับเฉพาะสิ่งที่ linker วางลงอิมเมจจริง:
FreeRTOS กิน flash 33,479 ไบต์ (2.1%), IRAM 7,326 (3.6%), DRAM 3,856 (5.6%)
ส่วนกองของ Wi-Fi กิน flash ~65%, IRAM ~24%, DRAM ~45%

ถอด FreeRTOS ออกหมดได้คืนราว 33 KB แลกกับการต้องเขียนไดรเวอร์แฟลช, SPI ของจอ,
คอนโซล USB, LittleFS และการตั้ง PSRAM ใหม่ทั้งหมด — ไม่คุ้มที่ราคาไหนก็ตาม

**ถ้าจะให้ SmartOS คุมคอร์ 0 จริง ราคาคือ shim 63 ฟังก์ชัน** ซึ่งเกือบทั้งหมดคือ
ของที่ SmartOS มีอยู่แล้วในชื่ออื่น (critical section, คิว, mutex, semaphore,
การหน่วง, การอ่าน tick) แต่ `ksync.h` ยังขาด timeout, recursive mutex,
task notification และ priority inheritance ก่อน

**และมีกำแพงที่ขยับไม่ได้:** `libpp` `libphy` `libnet80211` เป็นไบนารีปิดที่ต้องการ
พฤติกรรมและจังหวะเวลาของ FreeRTOS จริง **ตราบใดที่ยังต้องการ Wi-Fi คอร์ 0
เป็นของ SmartOS ไม่ได้** shim จึงได้น้อยกว่าที่คิดมาก

**สิ่งที่ทำแทน:** เลิกจ่ายค่าของที่บอร์ดไม่ได้ใช้ วัดทีละขั้นบนบอร์ดจริง

| | flash | RAM ภายใน |
|---|---|---|
| บัฟเฟอร์เทสยืมแล้วคืน แทนที่จะถือตลอดชีวิตบอร์ด | +388 | **−6,016** |
| SoftAP และ WPA2-Enterprise ที่บอร์ดนี้ใช้ไม่ได้ | **−48,048** | −192 |
| IPv6 ใน lwIP ที่ไม่มีอะไรในระบบพูด | **−23,452** | −1,504 |
| ไฟหลังขับด้วยรีจิสเตอร์ แทนไดรเวอร์ของ IDF | **−5,992** | −148 |
| | **−70,732** | **−7,712** |

RAM ภายในที่ว่างจริงบนบอร์ดตอนไม่ทำอะไร: 105 KB → 113 KB
**คง WPA3/SAE ไว้โดยตั้งใจ** เพราะเราเตอร์สมัยนี้ตั้งเป็น WPA3 และตัวที่แพงคือ
ใบรับรอง ไม่ใช่ handshake

### A1 — เลิกจ่ายค่าของที่ไม่ได้ใช้

คำถามที่เป็นจุดเริ่มคือ "ทำให้ SmartOS แทน RTOS แล้วยึดทั้งชิปได้ไหม" คำตอบที่วัดได้
อยู่ใน [ถ้าจะเอาคอร์ 0 มาด้วยล่ะ](#ถ้าจะเอาคอร์-0-มาด้วยล่ะ) และไม่ใช่คำตอบที่คำถามคาดไว้:
**FreeRTOS กินแฟลช 2.1% ส่วนกอง Wi-Fi กินราว 65%** งานจึงกลายเป็นการเลิกจ่ายค่าของ
ที่บอร์ดไม่ได้ใช้ — **คืนแฟลช 76,660 ไบต์ และ RAM ภายใน 7,844 ไบต์** พร้อมกับที่
ชุดทดสอบเพิ่มจาก 48 เป็น 75 เคส

ข้อที่ควรเล่าซ้ำ: **บัฟเฟอร์ของชุดทดสอบสามก้อนนั่งอยู่ใน `.bss` ตลอดชีวิตบอร์ด** —
6,016 ไบต์ของหน่วยความจำที่หายากที่สุดบนชิป ถูกถือไว้ให้เทสที่จบก่อน launcher ขึ้นจอ

### สิ่งที่รีวิวเจอ

สองรอบ สิบข้อ แก้หมดแล้ว ข้อที่สำคัญ:

**`#define` ใน `main.cpp` บอกอะไร `system.cpp` ไม่ได้** — `main.cpp` ตั้ง
`SMARTOS_KERNEL_TEST_BUILD` เพื่อบอกว่า "บิลด์นี้ไม่มี app manager" แต่ `#ifndef`
สองที่ที่ใช้มันอยู่ใน `system.cpp` ซึ่งมองไม่เห็น บิลด์ stress หกตัวจึงรันส่วนแอป
ทั้งก้อนทั้งที่ไม่มี app manager แล้วรายงานว่า Home กับตัวโหลดแอปพัง **ทั้งที่ไม่มี
อะไรพัง** และเป็นความผิดพลาดแบบเดียวกันเป็นครั้งที่สองในไฟล์นี้

**เลขล้นในเครื่องบายท์โค้ดเป็น undefined behaviour** — C++ ถือว่าเลขมีเครื่องหมาย
ล้นเป็นพฤติกรรมที่ไม่นิยาม โปรเจกต์นี้บิลด์ด้วย `-O2` และตัวเลขมาจากไฟล์ที่คนอื่น
เขียน มีการตรวจ `b == 0` แต่ไม่มีการตรวจ `INT32_MIN / -1` หรือ `-INT32_MIN`
หรือการล้นของ `+ - *` เลย ทั้งที่จุดขายของเครื่องนี้คือ *ทุกทางออกเป็น error
ที่ตรวจจับได้ ไม่ใช่ fault*

**`install` กับ `uninstall` สร้างพาธจากชื่อที่ไม่ตรวจ** — เชลล์มี `fs_path()`
("ใต้ /fs เท่านั้น ห้ามมี `..`") และ `cat` กับ `ls` ใช้มัน แต่สองคำสั่งที่
**เขียนและลบไฟล์** ไม่ใช้ `install ../sys/note 100` เขียนลง `/fs/sys/note.app` ได้จริง
ตัวป้องกันอยู่กับคำสั่งที่แค่อ่าน และหายไปจากคำสั่งที่ทำลายได้

**ไฟล์ 98 ไบต์จองพูลเคอร์เนลไปครึ่งหนึ่งได้** — การตรวจขนาดของตัวโหลดจำกัดโค้ด
สตริง และค่าคงที่ แต่ไม่จำกัดตัวแปรร่วมกับสแต็ก ซึ่งเป็นสองตัวที่ถูกคูณสี่ และ
`APP_KERNEL_MAX` ที่มีไว้ไม่ให้แอปไหนกินเกิน 32 KB ไม่ปรากฏในตัวโหลดเลย
พิสูจน์ด้วยไฟล์ที่สร้างมาเพื่อการนี้:

```
[appload] refused hungry: wants 64235 B, and no app may take more than 32768
```

**หน้า RAM โชว์ 284 KB แล้วเรียกว่าทั้งชิป** — ชิปมี 512 KB ส่วนต่างคือเฟิร์มแวร์ที่
ถูกวางตายตัวตอนลิงก์ ซึ่งไม่มีตัวเลข heap ไหนรายงาน และคืนไม่ได้ ตอนนี้หน้านั้น
แสดงครบทั้ง 512 KB

และข้อที่ไม่มีใครเจอเพราะมันเขียนไว้ตรงๆ: `include/smartos.h` สัญญาว่า
"mutex, semaphore และ queue **ทุกตัวมี timeout**" — **ไม่มีสักตัว** ตอนนี้เฮดเดอร์
ระบุของที่ยังไม่มีไว้ด้วย (ไม่มี timeout, ไม่มี recursive mutex, ไม่มี priority
inheritance, ไม่มี task notification) เพราะเฮดเดอร์สาธารณะที่พูดเกินจริงแย่กว่า
ไม่มีเฮดเดอร์

**ที่ผิดคือยอดรวม ซึ่งเป็นของบอร์ด ไม่ใช่ของ repo**

## หลักการเดียวที่ยึดตลอดโปรเจกต์

**ไม่อ้างอะไรที่ไม่ได้วัดบนบอร์ดจริง**

ทุกตัวเลขในเอกสารมาจากการทดสอบที่รันบนฮาร์ดแวร์ และบันทึกไว้ทั้งสิ่งที่สำเร็จ
**และสิ่งที่เข้าใจผิดไปก่อน** — เช่น race condition ข้ามคอร์ที่ทำให้บอร์ดวนรีบูต,
ตัวจัดคิวที่ทำให้งานตัวที่สามไม่ได้ CPU เลย, หรือหน่วยความจำที่ชนกับ Wi-Fi
จนบูตไม่ขึ้น ทั้งหมดเจอเพราะวัด ไม่ใช่เพราะเดา

รายละเอียดทั้งหมดอยู่ใน [README ฉบับภาษาอังกฤษ](README.md) ซึ่งไล่เรียงทีละ stage
ว่าสร้างอะไร วัดได้เท่าไหร่ และพังตรงไหนมาก่อน
